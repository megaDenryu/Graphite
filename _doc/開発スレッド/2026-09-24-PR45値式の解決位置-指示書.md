# PR #45: 値の式の名前を instance 宣言の位置へ固定する (実装の指示書)

## オーナーの裁定 (PR #45 コメント 2026-09-23T23:39:57Z)

案1 (構築用マクロの呼び出し位置で名前を解決し、すり替わりを仕様として許す) は採用しない。値ありの個体・積み荷の式は、instance 宣言を書いた位置の Rust の式として意味が決まる。構築の位置は「いつ構築するか」だけを決め、宣言された値の式が「何を参照するか」を変えてはならない。

回帰試験で固定する性質:
- instance 宣言の位置と構築用マクロの呼び出し位置に同名の識別子があっても、instance 宣言の位置の意味を保つ
- 関数のローカル変数・引数・型引数を、instance 宣言の位置から通常の Rust の式と同じ意味で参照できる
- 値の式は1回だけ評価される
- 値の式を生成ファイルへ複製しない
- `non_local_definitions` を発生させない

「呼び出し位置による名前のすり替わり」を正常な挙動として固定した回帰試験 (crates/graphite/tests/static_value_expr_name_resolves_at_call_site.rs) は、この方向では残さない。上の性質を確かめる試験に置き換える。

オーナーの 2026-09-23T18:23:47Z のコメントの9条件 (値ありは DSL の式からのみ、値なしだけ実行時供給、1回だけ評価、生成ファイルへ複製しない、non_local_definitions なし、異なる Nodes/Edges を組み合わせられない、内部識別子を不要に露出しない、回帰試験) も引き続き満たす。

## 親の設計の方向 (実測で確かめてから採否を決めよ)

- 名前を宣言の位置で固定するには、式を宣言の位置で束縛する。instance が関数の中 (文の位置) にあれば、宣言の位置で `let` によりクロージャを束縛する (クロージャはローカルを捕捉し、項目名は宣言の位置で解決される)。構築用マクロは、宣言の位置に置いた内部用の `macro_rules!` を通してこのクロージャを呼ぶだけにする。macro_rules の本体のローカル変数は定義の位置で解決されるので、内部用マクロの本体からクロージャの束縛名を参照すれば、呼び出し位置に同名のローカルがあっても宣言の位置の束縛を指すはずである (実測で確かめよ)。
- instance がモジュールの最上位 (項目の位置) にある場合、ローカルは存在しないので、式を宣言の位置の項目 (例: 捕捉しないクロージャを入れた `const`、または関数) として固定できる。
- マクロは自分が文と項目のどちらの位置で呼ばれたかを知れない。1つの書き方で両方に対応する手段が無いかをまず実験し、無ければ、関数の中の instance を見分ける最小の印を DSL に足す案 (例: instance の宣言の先頭の語を変える、`let` で受ける形にする) を比べて、利用者の書き方の差が最小のものを選べ。選んだ形と理由、棄てた案を報告せよ。生成器 (cli) の instance の探索もこの印に追随させる。
- クロージャが値を move する式 (例: `社員 { 名前 }` が String のローカルを move する) では、構築は1回しかできない (FnOnce)。この挙動が通常の Rust の意味と一致することを文書に書き、試験で固定せよ。

## 追加のレビュー (PR #45 コメント 2026-09-23T23:54:59Z): 単一の構築入口

オーナーは、公開の構築 API `construct::nodes!` → `construct::edges!(&nodes)` → `Graph::new(&edges)` の3段階を、生成コード内部の構築手順の漏れ出しと見なし、「静的グラフを実体化する」1操作の単一の入口 (例: `let graph = 開発チーム::construct!(値なしの個体の実行時の値);`) にできるか設計するよう求めた。3行を1つのマクロで包むだけでは不十分で、中間の状態を公開契約から外すことが目的である。値の式の名前を宣言の位置で固定する裁定と合わせて行う。

親の見立て: `Graph` が `Nodes` と `Edges` を所有し、`Edges` は `&Nodes` を持たず個体の位置で端点を表す。個体参照・辺参照は `graph.node_refs()` 等が `&self` を借りて作る。`Nodes`・`Edges`・`NodeRefs`・`EdgeRefs` を公開の型として残す必要があるかも見直す。
