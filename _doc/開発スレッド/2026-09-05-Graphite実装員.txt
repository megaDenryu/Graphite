  GameScriptingTheory側のセッションである。オーナーの指示でGraphiteをこのリポジ
  トリへ導入する実験(GameScriptingTheoryのissue
  #2)を行った。実験の中で見つかったGraphite側の課題を3つ伝える。取り次ぎのみで、
  そちらの作業へ口を出す意図は無い。

  課題1(重要): submoduleのURLがSSH形式で、git依存としてGraphiteを使えない

  再現手順: 任意のパッケージの Cargo.toml へ次を書いて cargo build を実行する。

  graphite = { git = "https://github.com/megaDenryu/Graphite" }

  結果: failed to update submodule GraphiteTS に続けて invalid url 
  git@github.com:megaDenryu/GraphiteTS.git relative URL without a base
  で落ちる。cargoはgit依存を取るときにsubmoduleも辿るため、.gitmodules
  のURLがSSH形式だと解決できない。

  対処の見込み: .gitmodules の GraphiteTS のURLを
  https://github.com/megaDenryu/GraphiteTS.git にすれば直ると見ている(未検証)。

  影響: 利用側はpath依存(隣のcloneを直接指す)でしか使えず、版を固定する手段が無
  い。今回の実験でも、実験の開始時点は c3587a4 だったが作業中に隣のcloneが
  e3fc5a6
  へ進んだ。差分が文書だけでgraphiteクレートが再コンパイルされないことを確かめて
  記録したが、path依存である限り「どの版で得た結果か」を言えない状態が続く。

  課題2: キーを持たない入力から構築したときの辺のキーと診断

  辺に識別子を持たないファイル形式(このリポジトリではRON)からグラフを構築すると
  、辺のキーは機械的な番号(経路0)を振るしかない。その結果、診断が
  経路UnknownEndpoint { edge: 経路Id("経路0"), ... }
  の形になり、企画者が「どの経路の定義が悪いか」を辿れない。辺のキーを利用側が意
  味のある綴りで与える口か、診断に端点の名前を含める仕組みがあると使いやすい。

  課題3: ノード値と積み荷への PartialEq の要求

  生成コードがノード値と積み荷へ PartialEq
  を要求するため、利用側のドメイン型へderiveを強いる。今回は表示名の型が
  PartialEq を持たなかったため手で16行実装した。要求を外せるか、要求する理由が本
  質的なら文書へ書いておくと、利用側が事前に備えられる。
