# PR #45 の静的グラフ構築境界の最終形: 実装の指示書

## オーナーの方針 (PR #45 のコメント 2026-09-23T18:23:47Z)

#46 へ分けず、PR #45 の中で値供給・構築経路を一度だけ最終形へ設計し直す。同時に満たす条件:

1. 値ありの個体・積み荷は DSL に書かれた式からのみ供給される
2. 値なしの個体だけを利用者が実行時に供給できる
3. 値の式は、呼び出し元のローカル変数・引数・型引数を参照できる
4. 値の式は1回だけ評価される
5. 値の式を生成ファイルへ複製しない
6. `non_local_definitions` を発生させない
7. 異なる `Nodes` / `Edges` を組み合わせて不整合な Graph を作れない
8. 橋渡し用の内部識別子・補助 API を利用者の名前空間へ不要に露出させない
9. これらの不変条件を回帰試験 (compile-fail を含む) で固定する

前回のレビューの条件も保つ: instance を関数の中に置いてよい / 生成 module を instance のスコープへ引きずり込まない / 利用者向けの配置規則が不要 / 値の式は利用者のスコープで型検査される。

## レビューのブロッカー6件 (`gh api repos/megaDenryu/Graphite/pulls/45/reviews` で全文を読め)

- A (17:31): `Nodes::new`・`Edges::new` が全引数を受け取り、値ありの個体・積み荷を差し替えられる。`Nodes` の個体フィールドが `pub` で、構造体リテラルからも迂回できる。橋渡し用の構築子は C 分類 (内部) に閉じ、B 分類の公開契約にしない。
- C (17:44): `Graph::new(&nodes2, &edges1)` のように、別の `Nodes` から作った `Edges` を組み合わせられる。`NodeRefs::new`・`EdgeRefs::new` も同じ。「異なる Nodes から作った Edges を同じ Graph へ渡せない」を回帰試験で固定する。
- D (17:47): 組み立て関数 `開発チームの個体を組み立てる`・`開発チームの辺を組み立てる` が利用者の名前空間へ漏れる (同名の利用者関数と E0428)。構築操作は、instance module など Graphite が所有する名前空間から辿れるようにする。
- F (17:49、issue #46): 値の式が入れ子の `fn` の中にあるので、ローカル・引数・型引数を捕捉できない。ローカルを捕捉する compile-pass の回帰試験を足す。
- B (17:43): 生成器 (crates/graphite-cli の schema_macro_collector・static_resolution) が、マクロ呼び出しのパスの最後の識別子だけで照合し、`src` と `tests` を含むパッケージ全体で1つの `schema名 -> schema` の名簿を作る。integration test は別 crate なのに同じ名簿に入る。受理条件: 別 crate・別 Cargo target を同じ名前空間に混ぜない / module が違うだけの同名 schema を禁止するなら理由を裁定として書く / 最後の識別子の一致だけで別スコープの schema へ誤結合しない / 回帰試験。
- E (17:48): 生成後の Rust 識別子の衝突を DSL の検証で検出していない。node 名 == edge 名 (`太郎Ref` が2つ)、端点の役割名 == 積み荷の役割名 (`member` が2つ)、具体辺名 == `{個体}Ref` の固定メソッド名 (`entity`)。この3つを検証層で検出し、回帰試験 (compile-fail) にする。

## 親の設計の候補 (実測で確かめてから採否を決めよ)

A・C・D・F は同じ「値の供給と構築」の層に属する。親の第一候補は次の形である。

- instance の展開は、値の式を本体に持つ内部用の `macro_rules!` (C 分類の名前、例: `__graphite_values_開発チーム`) を呼び出し位置に置く。
- 生成ファイルの instance module は、構築用のマクロを持つ (例: `macro_rules! 構築 { .. }` と `pub(crate) use 構築;` で `開発チーム::構築!(開発部: 部署 { .. })` として呼べる形)。構築用のマクロは、内部用のマクロを呼んで値の式を展開し、全部の値を受け取る内部の構築子 (C 分類、`#[doc(hidden)]`) へ渡す。
- 構築用のマクロを使った位置で値の式が展開されるので、同じ関数の中ならローカルを参照できる (macro_rules の衛生規則: ローカル変数は定義位置で、マクロ名は呼び出し位置で解決されるはず。実測で確かめよ)。impl を出さないので `non_local_definitions` も出ない。
- `Nodes` の個体フィールドは `pub` をやめ、値の読み出しは参照経由 (`entity()` 等) にする。
- C の対策: 構築の結果を1つの値にまとめるか、`Edges` が自分の由来の `&Nodes` を保持し、`Graph` と参照集合は `Edges` だけを起点に作る (`Graph::new(&edges)` の形)。`NodeRefs::new`・`EdgeRefs::new` は内部 (C 分類) に閉じる。

候補が成り立たない場合は、別の形を実験して選べ。公開 API は変わってよいが、変化は最小にし、選んだ理由と棄てた案を報告せよ。

B の親の方針: 生成器の探索の単位を Cargo target にする (`src/` の lib・bin、`tests/*.rs` の各ファイル、`examples/` 等はそれぞれ別の名前空間)。同じ target の中では static schema 名を一意とする (生成器は Rust の module の名前解決を再実装しないので、同じ target の中の同名 schema を区別できないため。この理由を docs/static_graph.md と docs/code_generation.md に裁定として書く)。instance の照合は同じ target の名簿だけで行う。
