## 5. 地雷と環境制約

- **IDE 診断 (rust-analyzer) はサブエージェントの中間状態を拾って偽のエラーを出す。** 判断は必ず `cargo build`/`cargo test` の実測で行う (メモリにも記録済み)
- **`cargo test --workspace` は examples を1件も実行しない** (ワークスペース非メンバー)。各 example ディレクトリで個別に `cargo test` (合計140件)
- **`verification/external-crate` の再生成は `cargo xtask generate` の対象外。** `cargo build -p graphite-cli` の後、当該ディレクトリで `target/debug/cargo-graphite.exe graphite generate`
- **生成テンプレートを変えたら全パッケージ再生成 + `docs/desugaring_reference.md` の引用追随が要る。** `check-docs` の2判定 (行範囲=先頭3行・鮮度=全行がファイル全体に実在) が検出する。参照とフェンスの間に散文があると照合対象に入らない (母数として報告される)
- **`quote!` の中の `///` は生成コードの公開面。** 撤去してはならない。`syn` で項目の doc 属性の行番号だけを取る手法が確立している (#22 段階5)
- **Bash の cwd が前のコマンドの `cd` で移動したまま残ることがある。** `cargo xtask` は「リポジトリルートで実行してください」と落ちる。絶対パスで `cd /c/devs/Graphite &&` を付ける
- **HEAD が detached になっていることがあった** (#28 着手時に d3d35cb で detached。原因未特定。レビュー員の `git worktree` か `filter-branch` の影響の可能性)。実装員は `issue28-line-counts` ブランチへ積み、親が ff-merge した。作業開始時に `git branch --show-current` を確認する
- 作業用 clone には `refs/codex/turn-diffs/checkpoints/...` の極端に長い ref があり、`file://` の git 依存として指すと Windows のパス長制限で失敗する (origin には無い)
- `文章チェック員` は 2026-09-05 まで Bash を持たず差分を読めなかった。以後は Bash 付き
- `cargo xtask check-line-counts` と `check-doc-comments` は `cargo test` に接続済み/未接続が違う: `check-doc-comments` は接続済み (`xtask/tests/doc_comments_check.rs`)、`check-line-counts` は未接続 (再設計待ち16件が残るため)

## 6. 学びと注意

- **粗い実測で断定して誤った (2回)。** 「生成コードの doc 欠落0件」は行頭 `pub` の grep で列挙のバリアントとフィールドを見落とし、実際は627件だった。「#16 → #21 → #22 の順」の提案は #16 が完了済みなのを見落とした。数える対象を型で決めてから数える。経緯は逐語の #22 段階1 付近
- **検査器は「違反0」の裏で母数を落とす。** check-docs は63件照合の裏で72件のフェンスを見ておらず、その中に虚偽の指紋値と2行ずれが埋もれていた。母数を報告させることが取りこぼしを見える化する唯一の手段。この学びはグローバル CLAUDE.md の節として制定済み
- **実装員の「確認済み」「検査済み」は自己申告。** 親の実測と親が派遣した検査員の結果だけを証拠にする。実装員が段階5で「語を落とさず畳んだ」と申告した57行から4件の語が落ちていた
- **検査員は並行で出す。** §0.5 の直列既定は編集を伴うエージェントの話 (オーナー裁定、規範へ追記済み)。片方の条文だけ読んで判断した誤り。経緯は逐語の「なんで検査員の規範は直列なんだ」付近
- **文章チェック員が差分を読めないと既存の状態を新規の指摘にする。** 道具の欠落は検査結果の信頼度を下げる。検査員の定義を派遣前に読む
- **レビュー員は毎回実害を見つけた。** 12回の検収で実害0回は3回だけ。検収を省く判断は今後もしない
- **診断の文言は企画者 (非プログラマ) の語彙で書く。** 「解決できません」(resolve の直訳) → 「見つかりません」、理由「宣言したID型のため」は文書へ移して診断は「表示できない」で止める (#26)
- **設計の対立は原則に照らして決着する。** #27 の条件付き導出 vs 全廃は、既存の `Debug` 実装の方針との一貫性と原則3 (Rust の直感) で条件付きに決着。親の直感 (全廃) は撤回した
- **腐る値を文書に書き写さない。** 指紋の値を書いた引用は生成器を変えるたびに腐る。値を書かない形へ変えた (#31)
- **ユーザーの指示「やるべきことをやれ」以後、確認質問はしていない。** 判断は規範と issue 記録で行い、所有者判断が要るものは issue に選択肢と推奨を書いて先へ進む
